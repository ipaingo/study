# Нейросети: Диагностика и исправление ошибок в коде

Ошибки в коде — это нормальная часть работы. Они случаются у всех — от новичков до опытных специалистов. Иногда код не запускается или ломается на ровном месте, а иногда работает, но выдаёт совсем не то, что ожидалось.

Раньше для диагностики и исправления ошибок кода приходилось бесконечно искать похожие случаи на форумах и читать десятки разделов «вопрос — ответ». Сейчас искусственный интеллект может быстро объяснить ошибку, предложить исправления и даже показать несколько способов решения.

ИИ будет максимально полезен, только если вы предоставите ему полный и правильный контекст — сам код, текст ошибки и описание того, что этот код должен был сделать. В этом уроке расскажем, как диагностировать ошибки в коде с помощью ИИ. А начнём с того, какие вообще ошибки бывают.

Мы будем разбирать диагностику и исправление ошибок на примере Python-кода, но подходы универсальны: их можно применять и в SQL, и в любых языках, где вы работаете с данными.

## Типы ошибок в коде

Чтобы правильно диагностировать и исправлять ошибки, нужно знать, какие типы ошибок бывают.

**Синтаксические ошибки.** Код даже не запускается.

Примеры: пропущенная кавычка, лишняя скобка, неправильно написанное ключевое слово.

Сообщения интерпретатора Python обычно начинаются с SyntaxError.

**Ошибки исполнения.** Код запускается, но ломается в процессе работы. Такие ошибки часто связаны с неожиданными данными.

Примеры:

- "ZeroDivisionError: division by zero" — деление на ноль.
- "KeyError: 'column'" — обращение к несуществующему столбцу.

**Логические ошибки.** Код работает и даже выдаёт результат, но результат неверный.

Пример: вместо среднего чека функция считает среднюю сумму заказа без учёта пользователей.

Это коварный тип ошибок: они незаметны, пока вы не сравните результат с ожиданиями.

**Ошибки валидации данных.** Код технически работает, но данные «ломают» логику.

Примеры:

- пустая таблица;
- в колонке чисел оказались строки;
- отрицательные значения там, где их быть не должно.

Соедините ошибку с типом, к которому она относится.

Не все ошибки приводят к падению кода и выводу текста на экран. Ошибки синтаксиса и исполнения дают явные сообщения, но логические и валидационные часто «тихо» искажают метрики.

Как вам задача?

Часто ошибки встречаются не по одной, а в комбинации. Сообщение интерпретатора может указывать на одно место, а настоящая причина кроется совсем в другом. Поэтому при отладке важно держать в голове контекст задачи. Именно этот контекст для диагностики нужно правильно передавать ИИ — тогда он сможет помочь не только «потушить пожар», но и подсказать, как не допустить его снова.

## Как диагностировать ошибки с помощью ИИ

Рассмотрим пример. Представьте, что вы написали функцию, которая считает средний чек на пользователя.

```
def avg_check(df):
    return df['amount'].sum() / df['user_id'].nunique() 
```

При запуске она вроде работает, но периодически возвращает ошибку: _ZeroDivisionError: division by zero._

Какие данные нужно предоставить ИИ в этом случае?

Неправильный ответ

Только сам код

Только по коду ИИ не поймёт, в чём проблема.

Код и текст ошибки

Тоже правильный ответ

Код, текст ошибки, ожидаемое поведение метрики и примеры данных

Все эти параметры помогут ИИ правильно понять контекст и выдать релевантный результат.

Текст ошибки и описание данных на вход

Как вам задача?

Чтобы ИИ действительно помог с ошибками, ему нужен полный и точный контекст. Без него модель будет «угадывать» и часто промахнётся.

Полный контекст — это не просто техническая детализация. Он позволит увидеть проблему в системе, где она реально возникает: с учётом реальных данных, среды, бизнес-смыслов и даже человеческого фактора.

Рассмотрим, что может входить в полный контекст.

**Минимальный воспроизводимый пример (MRE — Minimum Reproducible Example)**

Как с ним работать:

- Добавить фрагмент кода, который **гарантированно** воспроизводит ошибку.
- Если код большой, выделите 10–30 строк вокруг места ошибки.

В нашем примере про средний чек можно просто прислать только саму функцию. Но не всегда понятно, с какими входными данными или в каком сценарии возникает ошибка.

Лучше всегда добавлять пример вызова — даже если это всего две строки, это экономит время и делает диагностику точнее.

```
def avg_check(df):
    return df['amount'].sum() / df['user_id'].nunique()

# Вызов функции
import pandas as pd
df = pd.DataFrame({'user_id': [], 'amount': []})
avg_check(df)  
```

**Полный текст ошибки (stack trace)**

Как с ним работать:

- Добавить текст ошибки целиком, включая stack trace и строку или файл с ошибкой.
- Не обрезать самое важное место — последнюю причину. Stack trace часто указывает не только, что сломалось, но и где и почему.

Пример:

```
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
  File "<stdin>", line 2, in avg_check
ZeroDivisionError: division by zero
 
```

Важно, какая строка вызвала ошибку и что происходило до этого — иногда ошибка бывает вообще не в той функции, в которой ожидалось.

**Ожидаемое поведение (бизнес-смысл)**

Как с ним работать:

- Важно указать, что именно код должен был сделать или посчитать и в каком формате.
- Добавить пример корректного результата или формулу метрики.

Этот пункт особенно важен для диагностики и решения логических ошибок. Иногда всё работает по документации, но не так, как задумывал автор.

Вот как это можно реализовать для нашего примера:

Расчёт среднего чека пользователей, округлённого до 2 знаков после запятой.

Формула = сумма заказов/уникальное количество пользователей

Также можно добавить пример ожидаемого результата при различных граничных случаях:

```
Если пользователей нет - вернуть 0.

Пример корректного результата:
Вход: user_id = [101, 102, 103], amount = [500, 250, 250]
Ожидание: 1000 / 3 = 333.33 
```

**Примеры данных / структура**

Даём ИИ следующий контекст:

- 5–10 строк `df.head()` или синтетический пример;
- схему: столбец → тип → смысл, граничные значения, допускаются ли `NaN`, отрицательные числа и другие параметры.

Запрос может выглядеть так.

```
df:
user_id:int — идентификатор пользователя
amount:float — сумма операции, возможны NaN

Примеры:
1. пустой df
2. df 
user_id,amount
1,NaN
1,502
2,200 
```

**Окружение (при необходимости, в зависимости от типа ошибки)**

Дополнительно при необходимости можно указать:

- Версии библиотек или другую важную информацию. Иногда ошибка связана именно с несовместимостью версий или особенностями среды.
    
- Где исполняется код: в ноутбуке, скриптом, в пайплайне, через API.
    
- Ранее предпринятые попытки исправления.
    
- Зависимости и связанные функции (если функция ссылается на сторонние модули или функции, которые нужно тоже учитывать при поиске ошибки).
    

Такой структурированный подход помогает значительно сократить время на диагностику и делает процесс исправления ошибок более осмысленным и эффективным.

Необязательно использовать абсолютно все перечисленные пункты, но чем полнее контекст, тем выше шанс получить адекватный совет и реальное исправление, а не временное решение.

Соотнесите текст с типом контекста, к которому он относится.

MRE + полный текст ошибки помогают избежать «угадывания» контекста моделью. Ожидания фиксируют правило для пустых данных. Примеры данных показывают типы/NaN. Указание версий помогает, если баг зависит от библиотек.

#### Chain-of-Thought подход к отладке кода

Если просто попросить модель «Исправь», она выдаст решение, которое трудно проверить. Когда мы просим план по цепочке размышлений, модель фиксирует логику. Это помогает понять, какие шаги сделаны и почему, и снижает риск «починили одно — сломали другое».

Давайте вспомним, что характерно для этого подхода.

#### Как применить Chain-of-Thought для диагностики и отладки

В запросе чётко укажите, какие этапы анализа и ответа вы ожидаете. Вот примерная структура промта для примера с некорректно работающей функцией:

1. Кратко классифицировать проблему (тип ошибки: синтаксиса, исполнения, логики, валидации).
2. Дать короткий план исправления из 4–6 шагов.
3. Показать исправленный исходный код (с минимальными комментариями).
4. Дополнительно провести проверки «до/после» на трёх наборах данных (отдельным кодом):
    - нормальный (рабочий);
    - граничный (пограничные значения);
    - некорректный (ошибочные данные).
5. Одним предложением сформулировать первопричину и способ предотвращения ошибки в будущем.
6. Требования к ответу: сначала «План», затем «Код», затем «Проверки», затем «Причина». Без длинных рассуждений.

def avg_check(df):
    df = df.copy()
    df['amount'] = df['amount'].fillna(0)
    users = df['user_id'].nunique()
    if users == 0:

    return round(df['amount'].sum() / users, 2)

def paid_sum(df):
    required_cols = {'status', 'amount'}
    if not required_cols.issubset(df.columns):

### Подведём итоги

Для полной диагностики важно дать ИИ максимум контекста — код, ошибку, схему данных, примеры и граничные случаи.

Подход Chain-of-Thought позволяет подходить структурно, вы задаёте чёткую последовательность действий, необходимых для исправления:

- классифицировать ошибки;
- дать план исправления;
- показать исправленный код;
- провести проверки на разных данных;
- сформулировать причины и профилактики.

Чёткий промт — устойчивый результат: чем подробнее ваш запрос, тем точнее ИИ выдаёт не только исправление, но и объяснение логики. А это помогает вам лучше учиться находить и предотвращать ошибки.
