## 5.2. Окно наблюдения: когда смотреть на результаты и почему нельзя (или иногда все-таки можно) подглядывать

**Окно наблюдения** — заранее определенный период и объем данных, по которым команда оценивает результат эксперимента. Оно помогает не принять временный эффект за устойчивый и дождаться данных по метрикам, которым нужно время для созревания.

Окно наблюдения необходимо по нескольким причинам.

**Эффект новизны (novelty effect).** Пользователи активнее взаимодействуют с изменением просто потому, что оно новое. В первые дни функция может показывать завышенные метрики, которые затем снижаются по мере того, как интерес проходит.

Попробуйте вспомнить похожую ситуацию из собственного опыта. Если вы регулярно пользуетесь каким-то банковским приложением, сколько времени уходит на то, чтобы привыкнуть к новому расположению истории операций после редизайна?

Есть и обратный сценарий — **эффект привыкания (primacy effect)**. Изменение привычного интерфейса сначала раздражает и может ухудшать метрики: пользователи ищут кнопку на старом месте, совершают ошибки, тратят больше времени — а через неделю-две адаптируются. Любой крупный редизайн проходит «долину гнева»; решение по первым дням эксперимента может оказаться ошибочным в обе стороны.

![[Pasted image 20261107163013.png]]

_Пример изменения наблюдаемого эффекта по дням: новизна может завышать ранние измерения, а необходимость привыкнуть к новому интерфейсу — занижать. По мере адаптации эффект стабилизируется_

**Недельная цикличность.** Вторник и суббота могут выглядеть как два разных продукта: меняются состав аудитории, сценарии использования и конверсия. 

Например, команда A/B-тестирования Ozon учитывает это в дизайне: чувствительность метрик она оценивает на периодах, кратных 7 дням, — 7, 14, 21, 28 дней — чтобы каждый день недели входил в окно одинаковое число раз. Минимальное разумное окно — одна полная неделя, типичное — 2–4.

**Медленные метрики.** Retention 30-го дня по определению требует дождаться 30-го дня после попадания пользователя в когорту, а влияние на отток подписки может проявиться только после следующего биллингового цикла. 

Для раннего решения иногда используют валидированный прокси — быстрое поведение, которое связано с интересующей нас долгосрочной метрикой. Например, если исторические данные показывают, что третий заказ за первый месяц хорошо предсказывает дальнейшее удержание, этот показатель можно использовать как ранний индикатор.

#### Подглядывание

Одна из самых распространенных ошибок в A/B-тестировании выглядит так: команда каждый день открывает результаты и останавливает тест, как только p-value впервые опускается ниже 0,05. 

Проблема в том, что p-value в ходе теста блуждает: при нулевом эффекте оно рано или поздно случайно коснется порога — если смотреть достаточно часто. Гарантия «5% ложных срабатываний» актуальна только для однократной проверки в заранее назначенный момент.

![[Pasted image 20261107163021.png]]

_Пример A/A-теста: траектория p-value по дням. Если остановиться при первом пересечении порога 0,05, случайное колебание можно принять за существующий эффект_

Команда A/B-платформы Ozon показала этот эффект с помощью [симуляции A/A-тестов](https://habr.com/ru/companies/ozontech/articles/712306/). При остановке эксперимента в момент первого статистически значимого результата ошибка I рода в их симуляции выросла примерно в 10 раз. Причина в том, что фактически команда многократно проверяет гипотезу и использует каждую проверку как новую возможность остановить тест.

![[Pasted image 20261107163026.png]]

_Цена подглядывания: доля ложных «побед» при честном дизайне и ежедневной проверке с остановкой на первом «значимом» результате (по мотивам симуляций Ozon Tech)_

Рассмотрим еще один пример. 

**Пример проблемы подглядывания.** На сайте был запущен A/B-тест. Через 2 дня менеджер решил посмотреть результат:

|   |   |   |   |   |
|---|---|---|---|---|
|**Variations**|**Conversion Rate Range**|**Percentage Improvement**|**Chance to Beat Original**|**Conv/Visitors**|
|Control|8,66% ±3%|—|—|110/1270|
|Variation 1|0,91% ±1%|−89,50%|0%|10/1100|
|Average Case|5,06% ±2%|—|—|120/2370|

Конверсия в оригинальном варианте (Control) — 8,66%. Конверсия в тестовом варианте (Variation 1) — 0,91%. Первое впечатление — нужно срочно остановить эксперимент, но это не так: данных еще слишком мало. 

Результат через 10 дней после начала эксперимента:

|   |   |   |   |   |
|---|---|---|---|---|
|**Variations**|**Conversion Rate Range**|**Percentage Improvement**|**Chance to Beat Original**|**Conv/Visitors**|
|Control|13,66% ±2%|—|—|870/6370|
|Variation 1|17,10% ±2%|+25,18%|95%|1060/6200|
|Average Case|15,35% ±1%|—|—|1930/12570|

Конверсия в тестовом варианте — 17,10%. Конверсия в оригинальном варианте — 13,66%. 

Как делать правильнее:

- **Зафиксировать длительность заранее** (из расчета чувствительности) и проверять значимость один раз — в конце. В процессе надо следить за здоровьем эксперимента: корректностью сбора данных, SRM, техническими ошибками и критическими изменениями guardrail-метрик.
- **Если возможность принять решение раньше действительно важна, используют последовательное тестирование.** Это математически корректные процедуры «подглядывания» с поправленными порогами (SPRT/mSPRT и родственники). 
    
      
    В российской практике подробный [разбор](https://habr.com/ru/companies/tbank/articles/876984/) такого подхода публиковал Т-Банк. Авторы показывают, как последовательное тестирование позволяет в ряде случаев сократить время до решения, сохраняя контроль статистических ошибок. При этом у метода есть ограничения: ранняя остановка может ухудшать точность оценки самого размера эффекта, а для медленно созревающих метрик преимущество последовательного анализа уменьшается.
    
- **Правило одного продления.** Продлить тест можно один раз и только по заранее описанному триггеру («эффект положительный, но интервал слишком широк»).
